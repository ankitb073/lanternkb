# Threat model

What we protect, from whom, and what we do not claim.

## Assets

- The content of indexed files.
- Secrets that may sit inside them (keys, tokens, passwords, private keys).
- The index database. **Vectors are as sensitive as text**: embeddings can be inverted to recover much of the original.
- Queries. None are stored; they live only in the server's memory (a cache of recent query embeddings).

## Threats and mitigations

| # | Threat | Mitigation |
|---|---|---|
| T1 | Network attacker | No listener in the core: the MCP server speaks over stdio only and never binds a port; sync opens no sockets (tested with an audit hook), and extraction workers are denied the network (macOS). The optional settings page listens on 127.0.0.1 only while it is open (T10). No telemetry, ever. The only network use is `lanternkb models pull`, run by hand. |
| T2 | Other user or process reading the index | The index, its -wal and -shm files, and every config lanternkb writes are mode 600, in folders lanternkb creates with mode 700. A config written by hand, or a folder that already existed, keeps its own mode; `doctor` fails on one other users can read. Full-disk encryption (FileVault) is required, because the index holds the redacted text and vectors of every indexed file; `doctor` reports whether it is on. There is no encrypted-database option. New indexes are excluded from Time Machine, so a purge does not live on in backups. Same-user malware is out of scope (see below). |
| T3 | Secrets ending up in the index | Layered: path deny list, file-type gate, secret scan, redaction before chunking and embedding, files with a found secret made local-only, and an audit log of what was skipped or redacted (rule and location, never the value; a removed file's name leaves it). **Measured on held-out planted secrets, zero leaks beyond the scanner's misses each time.**<br>- Phase 2's split: 87.5% kept out (CI 84.9% to 89.7%; results).<br>- A second split in contexts nobody tuned for (2026-10-03): 78.0% for phase 2's rules and 82.7% with the rules added since.<br>- A third such split (2026-10-03): **71.9%** (CI 68.5% to 75.1%; results); 83% of plain-text secrets, 47% of secrets inside encodings (escaped, folded, split across XML, base64 in LDIF).<br>- Realistic clean files: 6% are flagged and so made local-only.<br>`scripts/check_secrets_regression.py` re-runs the planted corpus at each release. |
| T4 | Sensitive content reaching a cloud assistant | Tiers. The MCP server's tier is fixed when it starts (`--tier open` or `--tier all`), never by a request; every tool filters by it and re-checks each result against today's config, and an open server ranks keywords and vectors over open text only. `mcp-setup` prints one entry per audience. The all-tier server refuses a client that names itself a cloud assistant (Claude Code, Claude Desktop and others), which catches mistakes, not a client that lies. **Tiers bound what the MCP server returns, nothing else:** an assistant that can also run commands or read files as you (Claude Code can) could read local-only text through the files themselves, the index or the CLI, or loosen a tier in the config. As speed bumps, `lanternkb search` shows only open files when run inside Claude Code unless asked for more, and `mcp-setup` prints Claude Code deny rules for local-only folders, the index, the config and the CLI (see "Not claimed"). |
| T5 | Prompt injection: an indexed file contains instructions for the assistant | Results are returned as data with provenance and an `untrusted_content` marker, and the tool descriptions say so. No write, delete or execute tools. `sync` starts `lanternkb sync` for the server's own config at most every 10 minutes; it cannot change config, roots or tiers, and it never builds an index that does not exist yet. The server refuses a config another user owns or can change. One test checks the marker. **Observed (2026-10-03, results):** with only lanternkb's tools allowed, Claude saw 12 kinds of planted instruction 129 times in 24 sessions and followed none; one answer warned the user. One model, a small corpus: an observation, not a guarantee. |
| T6 | Path traversal and symlink escape | Resolve real paths. Allow only inside approved roots. Do not follow symlinks out of a root (a link into another root takes the stricter tier). `get_file_excerpt` re-checks policy and tier. |
| T7 | Malicious or huge files (parser exploits, decompression bombs) | Extractors run in sandboxed worker processes (macOS `sandbox-exec`, deny by default): no network; no opening of user files (the parent opens each checked file and hands over the descriptor), though file metadata anywhere and Python's code folders stay readable (`doctor` warns if one overlaps an indexed folder); no writes outside a private temp folder; no system services, drivers or child processes; no other processes' details (arguments, environment) and only an allow-list of system facts; no signals to other processes. Images and audio run on separate workers that may also start ffmpeg, tesseract or whisper-cli (nothing else) and open drivers. Local-only ones also use the GPU, the Neural Engine, Metal's compiler and their caches (one per user, shared with other programs); media workers whose output may be open get none of those, so no local-only worker can leave text there for them: they read images with Tesseract and transcribe on the CPU. The parent enforces time and memory on the whole family of a worker (its process group and every descendant). When a worker is closed or killed, every process whose working folder is inside that worker's private temp folder is killed too, so a helper that forked twice to leave the family dies with its worker; a helper that also changes its working folder is missed, and lives on inside the sandbox. Nothing unrelated is matched: the folder is new for each worker. Media workers of the two tiers never run at the same time (local-only first), and every local-only helper is killed before an open media worker starts; one that escaped the sweep could in principle hold a GPU surface that an open media worker looks up, which is not tested. Office files are checked for zip bombs and DOCTYPE tricks before parsing. An honest worker returns only redacted text, and the parent checks every reply's shape. Everything bound for open tier, and all plugin output, is scanned again by a scanner-only process that never parses a file. Text is scanned with its line breaks as it will be stored, the segments as one text; a chunk that holds a piece of a cut long line (more than 800 characters) is scanned once more as stored, because the cut makes new line starts. So a parser taken over by one file cannot pass along secrets unaltered; it could pass them along altered (split, encoded, or with look-alike characters), or pass along other text of files on the same worker (same kind and tier). A file is shown as open only if it was read on an open worker: one whose tier becomes looser is read again first. The parent computes each file's hash from the text it stores. Failures skip the file with a reason. On Linux (5.13 or later, with Landlock enabled), each worker sandboxes itself before it reads any file: Landlock lets it read only the system's and Python's code folders, a few files in /etc (the loader's cache, time zone, users and groups, certificates, MIME types, fonts) and the models folder for media, write only its temp folder, and run only its Python and the media tools; seccomp denies sockets and connecting, tracing or reading other processes, key rings, io_uring, BPF, mounts, new namespaces (`unshare`, `setns`, and `clone` with namespace flags), and signals to any process but itself. Since a worker cannot kill its own tool there, every tool also runs under a CPU-time limit from the kernel, and a worker stops waiting for a tool that overruns. From Linux 6.7 Landlock also denies TCP, and from 6.12 it keeps signals and abstract sockets inside the sandbox. A worker that cannot sandbox itself says why, the sync reports `extraction process` instead of `sandboxed`, and `doctor` warns. **Implemented in phase 4**, tightened in phase 9. |
| T8 | Supply chain (dependencies, models, plugins) | The repo pins direct and transitive dependencies in `uv.lock`, and CI installs with `--locked`; a published wheel can pin only its direct dependencies. No install-time code of our own. PyPI trusted publishing and an SBOM are release tasks, not done. Models are fetched only by `lanternkb models pull`, at a pinned revision for the embedder and the default audio models, weights and configs only (no code, no pickles), and not again once present. Plugins are off until enabled. Extractor plugins run sandboxed on workers of their own. Embedder and tier-rule plugins run with the user's privileges; `features list`, `features enable`, the settings page and `doctor` say so. Installing any Python package trusts its author (`.pth` files run at interpreter start); the plugin guide says so. |
| T9 | Stale or wrong results shown as fact | Every result carries its path, location (lines, page, slide or cells) and tier; `get_chunk` and `get_file_excerpt` add the index time and `file_hash`, the first 12 hex digits of the SHA-256 of the file's indexed (redacted) text. Every result is re-checked against today's config, and a file deleted since the last sync is not shown. |
| T10 | The settings UI's temporary local server is reached by another process or a web page (DNS rebinding, cross-site request) | Optional package, runs only on demand; exits when its last tab closes, after 150 s without a heartbeat, or after 10 idle minutes (never during a sync it started). Loopback only, random port, random path; a one-time token (valid 5 minutes, opened through a private file, never on a command line) exchanged for an `HttpOnly; SameSite=Strict` cookie scoped to that path; `Host`, `Origin` and `Sec-Fetch-Site` checks and a form token on every change; strict CSP, no framing, no CORS; nothing logged. All changes go through the validated control API and are audit-logged. Its search (2026-10-08) shows every tier, as the terminal does (open files only when started inside Claude Code), through the MCP server's own search, with today's config applied; queries are sent by POST with a form token and answered with a redirect to results kept in the page's memory under a random handle (Post/Redirect/Get), so they stay out of the address, the title, browser history and the saved session, and are never logged. An assistant that can drive the user's browser (computer use, a browser extension) could read local-only text from an open settings tab; that is an assistant acting as the user, which tiers do not claim to stop. Its "Show in Finder" button takes only a result id, reveals only a file today's config still shows, and never opens or runs it. The MCP server never loads the control API; its only write path is starting `lanternkb sync`, which changes no settings. |
| T11 | A feature or plugin overreaches (reads more than it says, hangs, exhausts memory) | Declared capabilities are shown in `features list` and on the settings page. Extractors: host-enforced limits (time, memory of the process group, output size), capped for plugins at 120 s, 2048 MB and 50 MB; deny-default sandboxed workers that open no user files, one set of workers per plugin, split by tier; plugin output and notes scanned again by a scanner-only process, findings checked by the parent. Embedder and tier-rule plugins run in-process: their calls have deadlines (a tier rule 2 s, then every file is local-only; a query embedding 30 s, then keyword search), and anything a tier rule raises, `SystemExit` included, makes the file local-only. Loading a plugin has a deadline too (30 s, then it fails closed), a stuck tier rule is not called again in this process until its call ends, and tier rules get 120 s per sync in all. The built-in reranker reads only results the server may show, and a call that fails or takes over 10 s leaves the search's own order; the server tries it again after 10 minutes. Skip reasons are short codes; notes are scanned, redacted, capped at 300 characters and shown only locally. Tier rules fail closed, including one that is turned on but not installed. Per-feature data namespaces; disabled and unknown features read nothing and show nothing. |

## Not claimed

- **Zero leakage.** Scanners have less than 100% recall: 71.9% on our latest held-out planted-secret split (87.5% and 82.7% on the earlier ones), and less inside encodings. We publish the measured rate and the known misses. Keep credential folders out with deny rules or local-only roots rather than relying on the scanner.
- **Protection from malware running as the same user** with the same file access.
- **Anonymity.** A cloud assistant that receives an `open` result sees it.
- **Tiers against an assistant that can act as you.** Tiers limit what the MCP server returns. An assistant with shell or file access can read your files or the index, run lanternkb's CLI, or edit the config; one that drives your browser can read an open settings page, whose search shows every tier. Restrict it with the client's own permissions (`mcp-setup` prints Claude Code deny rules), and keep confidential folders out of its working folder; a script it writes can get past such rules.
- **An untrusted config.** Whoever writes the config, or the `--config` an MCP entry names, decides what is indexed and at which tier. Register only entries you wrote.
- **Deletion beyond the index.** Purges and re-scans erase text from the index file, its WAL and its keyword index. New indexes are kept out of Time Machine, but other backups, APFS snapshots and freed SSD blocks are not touched (full-disk encryption covers the last).
- **Protection from third-party plugins you enable, beyond the sandbox.** An extractor plugin controls the text of the files it reads, so it could leak their content in a form no scanner recognises; embedder and tier-rule plugins run with your privileges. They are code you choose to run.

## Rules for contributors

- Never add telemetry or network calls to the core.
- Never log document text, secrets or queries. (`LANTERNKB_DEBUG_WORKER_STDERR`, for debugging only, can write worker tracebacks to a file you name.)
- Test fixtures must be synthetic. Fake secrets are clearly labelled and allow-listed in the repo's own secret scan.
